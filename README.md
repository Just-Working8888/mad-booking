# Бронирование переговорной

Интерфейс бронирования одной переговорной комнаты в пределах рабочего дня 09:00–18:00: дневной таймлайн, список броней, создание, редактирование и удаление с проверкой бизнес-правил на клиенте и на сервере.

- **Демо:** (https://mad-booking.vercel.app/?date=2026-10-18)
- **Затраченное время:**  4часа

## Стек

| | |
|---|---|
| Фреймворк | Next.js 16 (App Router), React 19, TypeScript (strict) |
| Данные | Redux Toolkit + RTK Query (только кэш серверных данных, без дублирующих slice) |
| UI | Ant Design 6, `@ant-design/icons`, SCSS Modules |
| Архитектура | Feature-Sliced Design |
| Mock API | Два режима: Next.js Route Handlers + in-memory хранилище (локально) или эмуляция API в браузере + localStorage (публичное демо) |
| Тесты | Vitest |

## Запуск

Нужен Node.js ≥ 20.9.

```bash
npm install
npm run dev        # http://localhost:3000
```

Другие команды:

```bash
npm test           # unit-тесты (vitest run)
npm run test:watch # тесты в watch-режиме
npm run lint       # ESLint
npx tsc --noEmit   # проверка типов
npm run build && npm start   # продакшн-сборка
```

По умолчанию работает **серверный режим**: запросы идут в Route Handlers, данные хранятся в памяти процесса и пропадают после перезапуска сервера.

Чтобы локально запустить **браузерное демо**, как на Vercel:

```bash
NEXT_PUBLIC_API_MODE=browser npm run dev
# или продакшн-сборка:
NEXT_PUBLIC_API_MODE=browser npm run build && npm start
```

Режим задаётся при сборке. Подробнее — в разделе «Серверный mock API и браузерное демо».

## Что реализовано

**Расписание**
- Выбор даты: стрелки «‹ ›», кнопка «Сегодня», полоса дней недели, календарь. Дата хранится в URL (`?date=YYYY-MM-DD`), поэтому работают перезагрузка, «Назад» и ссылки. Соседние дни подгружаются при наведении.
- Вертикальный таймлайн 09:00–18:00 с точностью до минуты: брони отображаются по фактическим минутам (например, 10:07–11:43), а не по сетке 30 минут.
- Визуально различаются свободное время, занятое, прошедшее (штриховка), идущая сейчас бронь, промежутки короче 30 минут (их нельзя забронировать) и линия текущего времени.
- Список броней дня с длительностью, статусом и сводкой «N броней · свободно X ч Y мин».

**Создание и редактирование**
- Клик по свободному времени открывает форму с готовым слотом: начало округляется до 15 минут, длительность 1 час, но не дальше следующей брони, 18:00 или 2 часов. Кнопка «Новая бронь» предлагает ближайшее свободное время.
- Форма: начало, кнопки длительности (30 мин · 45 мин · 1 ч · 1 ч 30 мин · 2 ч), окончание, необязательное название.
  - В выборе времени доступны только допустимые значения.
  - Кнопки длительности, которые не помещаются, выключены с объяснением.
  - Время можно уточнить до минуты с клавиатуры.
- Черновик брони сразу виден на таймлайне. Если он конфликтует, он красный, и рядом указано, с какой бронью пересекается.
- При смене начала длительность сохраняется. Если окончание меняется автоматически, форма показывает, что изменилось и почему («Длительность сокращена: 1 ч → 45 мин, дальше время занято. Окончание — 10:00»), и выделяет поле окончания.
- Начавшиеся и прошедшие брони открываются только для просмотра, их можно удалить. Если бронь начинается, пока её редактируют, форма заменяется предупреждением «Редактирование больше недоступно», где сказано, применены ли несохранённые изменения.
- Удаление с подтверждением.

**Бизнес-правила** (одни и те же функции проверяют их на клиенте и на сервере)
1. Начало и окончание в пределах 09:00–18:00.
2. Начало раньше окончания.
3. Длительность от 30 минут до 2 часов, время с точностью до минуты.
4. Брони не пересекаются. Касание границ (10:00–11:00 и 11:00–12:00) конфликтом не считается.
5. Нельзя бронировать прошедшие даты и время.
6. При редактировании бронь не конфликтует сама с собой.
7. Сервер может вернуть 409, даже если интерфейс считал слот свободным (см. ниже).

**Состояния интерфейса:** загрузка (скелетоны без прыжков вёрстки), пустой день, ошибка загрузки с «Повторить», отправка формы, успех (уведомление и подсветка брони), ошибки 409/404/422/сети, прошедшая дата (только просмотр), рабочий день закончился.

**Защита от потери данных и случайных действий**
- Если в форме есть несохранённые изменения, перед переходом к другой брони, другому слоту, другой дате или закрытием нижней панели касанием снаружи появляется подтверждение.
- Enter в поле времени только подтверждает время и не отправляет форму.
- Смена дня всегда закрывает форму, поэтому старая форма не появляется при возврате.
- Если открытую бронь удалил кто-то другой, пользователь получает сообщение.

**Адаптивность и доступность**
- **На телефоне:** закреплённая шапка с датами, переключатель «Расписание / Список», форма в нижней панели. Дни недели и строки списка — крупные зоны нажатия (52px). Блок 30-минутной брони на таймлайне ниже (32px), но список дублирует его полноразмерной строкой.
- **Клавиатура и скринридеры:**
  - свободные промежутки и брони — кнопки с понятными `aria-label`, список дублирует таймлайн;
  - при открытии формы фокус переходит в неё, при закрытии возвращается к элементу, который её открыл;
  - после 409 фокус ставится на время начала, после других ошибок сервера — на кнопку сохранения;
  - различия передаются не только цветом: прошедшее время заштриховано, черновик пунктирный;
  - учитывается `prefers-reduced-motion`.

## Архитектура

```
app/                      # Next.js: роутинг + слой app из FSD
  _providers/             # Redux store, AntdRegistry + ConfigProvider (ru_RU, тема)
  _store/                 # makeStore()
  api/bookings/           # Route Handlers — тонкий HTTP-слой mock-сервера
views/booking/            # слой pages из FSD (назван views, чтобы не конфликтовать с Next)
widgets/
  day-timeline/           # таймлайн дня
  day-agenda/             # список броней дня
features/
  select-date/            # навигация по датам + синхронизация с URL
  booking-editor/         # форма создания и редактирования (логика в useBookingEditor, moveStart)
  delete-booking/         # удаление с подтверждением
entities/booking/
  model/                  # типы, константы, чистые правила и функции расписания (без React)
  api/                    # RTK Query эндпоинты, разбор ошибок
  lib/, ui/               # useRoomNow, форматирование, BookingBlock / BookingListItem / BookingDetails
shared/
  api/                    # единственный createApi; транспорт можно подменить через store
  config/                 # API_MODE: server | browser
  lib/time/               # работа с HH:mm и YYYY-MM-DD
  styles/                 # брейкпоинты SCSS
server/bookings/          # mock-бэкенд вне FSD:
  service.ts              #   правила, статусы 404/409/422, атомарная проверка с записью
  repository.ts           #   интерфейс BookingRepository + in-memory реализация
  protocol.ts             #   контракт API без привязки к транспорту: разбор тела, ошибки → статус
  http.ts                 #   адаптер протокола к Request/Response для Route Handlers
demo-api/bookings/        # браузерное демо вне FSD: localStorage-репозиторий + RTK baseQuery
```

Ключевые решения:

- **Бизнес-логика — чистые функции** в `entities/booking/model` (`validateBooking`, `findConflict`, `getFreeIntervals`, `getMaxEnd`, `suggestSlot` и др.), без React и antd. Их используют и форма, и сервер, поэтому правил не два набора, а один.
- **Время сравнивается в минутах**, а даты обрабатываются как календарные строки `YYYY-MM-DD`, без `new Date("YYYY-MM-DD")` и сдвигов UTC.
- **Часовой пояс офиса.** «Сейчас» считается по часам офиса (`Asia/Bishkek`) одинаково в браузере и на сервере. Поэтому сервер в UTC (Vercel) и пользователь в другом поясе одинаково понимают, какое время уже прошло. Пояс задаётся одной константой `ROOM_TIME_ZONE`.
- **Сетевой слой отделён от UI.** Компоненты знают только хуки RTK Query. Чтобы перейти на настоящий API, достаточно поменять `baseUrl` в `shared/api`. Сервер импортирует только `entities/booking/model`, поэтому RTK и react-redux не попадают в Route Handlers.
- **Mock-сервер.** Сервер устроен по слоям: `Route Handler → service (правила, статусы) → BookingRepository (интерфейс)`. Хранилище в памяти — одна из реализаций интерфейса, её можно заменить, не трогая сервис. Браузерное демо использует тот же сервис и протокол, меняются только транспорт и репозиторий (см. ниже).
- **Атомарность.** Проверка пересечений и запись идут внутри `repository.transaction()`; в памяти это очередь промисов. Есть тест: из двух одновременных запросов на один слот проходит ровно один, без блокировки тест падает.
- **HTTP-статусы и формат ошибок.** Сервер отвечает 200/201/204, 400 (некорректный запрос), 404, 409 (пересечение) и 422 (нарушено правило). Ошибки всегда приходят в одном формате `{ error: { code, message, field?, conflict? } }`.
- **Никаких дублирующих данных в Redux.** Брони живут только в кэше RTK Query; состояние UI (открытая панель, черновик, подсветка) хранится локально в странице.

## Обработка 409

Конфликт — ожидаемая ситуация: между загрузкой расписания и отправкой формы слот мог занять кто-то другой.

1. **Сервер** проверяет пересечения атомарно и при конфликте отвечает `409` с телом `{ error: { code: "CONFLICT", message, conflict } }`, где `conflict` — бронь, которая занимает слот.
2. **RTK Query** при `409` (и `404`) инвалидирует теги: расписание нужной даты перезапрашивается само, без ручного `refetch`.
3. **Форма не закрывается и не теряет данные.** Время и название остаются, появляется предупреждение «Это время только что заняли…». Мешающая бронь подсвечивается на таймлайне, черновик становится красным, а фокус переходит на время начала. Кнопки длительности и выбор времени пересчитываются по свежему расписанию.
4. **Аналогично 404:** если бронь удалили, пока её меняли или удаляли, пользователь получает понятное сообщение, а расписание обновляется.

**Демо конфликта.** Переключатель «Имитировать конфликт» в шапке отправляет со следующим сохранением заголовок `x-simulate-conflict: 1`, и сервер отвечает 409.
- Срабатывает один раз и ничего не записывает в хранилище.
- Валидация, 404 и настоящий конфликт проверяются раньше и имеют приоритет.
- Настоящий конфликт можно воспроизвести двумя вкладками: открыть форму в одной, занять это время в другой и сохранить в первой.

## Серверный mock API и браузерное демо

Бизнес-логика, сервис, протокол ошибок и весь UI общие для обоих режимов. Различаются только транспорт и хранилище.

| | Серверный режим (`server`, по умолчанию) | Браузерное демо (`browser`, на Vercel) |
|---|---|---|
| Как идут запросы | RTK Query → `fetch` → Route Handlers `/api/bookings` | RTK Query → custom `baseQuery` прямо в браузере, без сети |
| Где проверяются правила | `server/bookings/service.ts` на сервере | тот же `service.ts`, но в браузере |
| Хранилище | in-memory `Map` в процессе Node.js | `localStorage` (ключ `meeting-room-demo:bookings:v1`) |
| Кто видит данные | все клиенты этого процесса | только этот браузер |
| После перезагрузки | данные сохраняются, пока жив процесс | данные сохраняются |
| Атомарность «проверка + запись» | очередь транзакций в процессе | очередь транзакций в пределах одной вкладки |
| Статусы и формат ошибок | 400/404/409/422/500, `{ error: { code, message, field?, conflict? } }` | те же |
| Имитация 409 | заголовок `x-simulate-conflict: 1` | тот же заголовок, обработка та же |

**Как это устроено**
- **Выбор режима.** `NEXT_PUBLIC_API_MODE` читается при сборке (`shared/config`). В `next.config.ts` он по умолчанию становится `browser`, если сборка идёт на Vercel (`process.env.VERCEL`), иначе `server`. Явно заданная переменная всегда побеждает.
- **Подмена транспорта.** Её делает слой app: `makeStore()` передаёт транспорт в `thunk.extraArgument`, а `baseQuery` в `shared/api` берёт его из `api.extra` или использует обычный `fetchBaseQuery`. Эндпоинты, теги, инвалидация и обработка ошибок в UI не менялись.
- **Браузерный транспорт** (`demo-api/bookings/browserBaseQuery.ts`):
  - разбирает URL и метод так же, как Route Handlers;
  - вызывает тот же `createBookingService` с тем же разбором тела из `protocol.ts`;
  - возвращает `{ data }` или `{ error: { status, data: { error } } }` — ту же форму, что и `fetchBaseQuery`;
  - данные проходят через JSON, как по сети;
  - добавлена задержка 250 мс, чтобы были видны состояния загрузки и отправки.
- **localStorage-репозиторий** реализует тот же `BookingRepository`:
  - каждое чтение берёт свежие данные, поэтому изменения из другой вкладки подхватываются при возврате на неё (`refetchOnFocus`);
  - повреждённый JSON или чужие и неполные записи игнорируются, приложение не падает, следующая запись перезаписывает хранилище корректными данными;
  - если запись не удалась (хранилище отключено или переполнено), API отвечает `500 INTERNAL_ERROR` с понятным сообщением, и форма сохраняет введённые данные.
- **SSR.** К `localStorage` обращаются только при выполнении запроса, а запросы выполняются в браузере после гидрации: время «сейчас» и сама страница расписания рендерятся только на клиенте. На сервере репозиторий возвращает пустой список и ничего не пишет.

**Чем браузерное демо не является.** Это эмуляция API внутри одного браузера, а не сервер:
- данные видны только в этом браузере и пропадают при очистке данных сайта;
- в других браузерах и у других проверяющих расписание своё;
- между вкладками нет атомарности: если две вкладки одновременно сохранят пересекающиеся брони, обе записи могут пройти, потому что `localStorage` не даёт транзакций между вкладками. В пределах одной вкладки проверка с записью сериализована.
- Обычный сценарий «две вкладки по очереди» работает корректно: вторая вкладка получает настоящий 409, потому что сервис перед записью читает свежие данные.

## Известные ограничения

- **Серверный режим:** данные в памяти процесса живут, пока жив сервер, и общие для всех посетителей. Поэтому на Vercel используется браузерное демо.
- **Браузерное демо:** данные хранятся только в этом браузере, между вкладками нет атомарности (см. выше), объём ограничен квотой `localStorage` (обычно около 5 МБ, этого с запасом хватает).
- **Перенос брони на другой день** API поддерживает, а в интерфейсе его нет: форма редактирует время в пределах выбранного дня.
- **Закрытие с потерей изменений.** Явные «Отмена» и «✕» закрывают форму без подтверждения, это осознанное действие. Кнопка «Назад» в браузере при открытой форме с изменениями тоже закрывает её без вопроса.
- **Одна переговорная**, без пользователей и авторизации, поэтому нет понятия «моя бронь» и прав на удаление.
- **Часовой пояс офиса** зашит константой (`Asia/Bishkek`).

## Деплой

Проект собирается на Vercel без дополнительной настройки (`next build`, Node ≥ 20.9). На Vercel автоматически включается браузерное демо (`NEXT_PUBLIC_API_MODE=browser`); задать режим явно можно переменной окружения проекта.

Почему не серверный режим: Route Handlers на Vercel выполняются в функциях, у каждого экземпляра своя память. Хранилище в памяти очищается, когда экземпляр простаивает, может расходиться между параллельными экземплярами и общее для всех посетителей. Браузерное демо этих проблем не имеет: каждый проверяющий работает со своими данными, и они переживают перезагрузку страницы.

## Что можно улучшить

- Общее для всех посетителей хранилище демо (например, Redis), а в реальном проекте — БД с ограничением на пересечения (например, `EXCLUDE USING gist` в PostgreSQL).
- E2E-тесты (Playwright) на ключевые сценарии: создание кликом, 409 с сохранением данных формы, 404 при удалении, несохранённые изменения.
- Перетаскивание и растягивание броней на таймлайне, перенос на другой день.
- Оптимистичные обновления в RTK Query для удаления.
- Индикаторы занятости на днях недели (сейчас API отдаёт брони только за один день).
- Тёмная тема на основе токенов antd.
